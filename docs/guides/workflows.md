# 常见工作流

> 在实际工作中使用 OKS 的典型场景和流程。

这里展示 4 个最常见的使用场景，每个场景都包含完整的操作流程和实践技巧。

---

## 工作流 1：日常学习

**场景**：看技术文章、视频、课程，想把学到的东西记住。

### 流程

```
1. 看到好文章/视频
   ↓
2. 收录到 OKS（对 Agent 说"收录这篇文章"）
   ↓
3. 周末集中审核 Drafts（15-30 分钟）
   ↓
4. 写方案/回答问题时自动召回
```

### 技巧

**平时只收集，不审核**
- 降低心理负担
- 避免打断学习节奏

**每周固定时间审核**
- 如周日晚上
- 形成习惯更容易坚持

**审核时批量处理**
- 一次处理 5-10 个
- 效率更高

### 示例

**周一到周五**：
- 看了 10 个技术视频
- 收录到 Raw（10 分钟）

**周日晚上**：
- 审核 10 个 Draft
- 晋升 3 个高价值 Wiki（20 分钟）

**下周工作**：
- 写方案时自动召回相关知识
- 节省调研时间

## 工作流 2：技术选型

**场景**：需要选择技术方案，需要对比多个候选方案。

### 流程

```
1. 列出候选方案（如 3 个 AI 模型）
   ↓
2. 收集每个方案的资料（官网、评测、视频）
   ↓
3. 沉淀每个方案的核心特性到 Wiki
   ↓
4. 召回对比 → 制作对比表 → 做出决策
```

### 技巧

**为每个方案建立 goal**
- 提升相关召回
- 例：`master-ai-model-selection`

**用统一的结构记录**
- 成本
- 性能
- 使用场景
- 优缺点

**对比时用召回**

```bash
oks recall "方案 A vs 方案 B" --limit 10
```

### 示例

**候选方案**：Kimi K3 / GPT-4 / Claude Opus

**第 1 天**：
- 每个方案收集 2-3 份资料
- 官网、评测、实测视频

**第 2-3 天**：
- 审核 Draft
- 沉淀为 3 个 Wiki 页面（核心特性 + 成本 + 场景）

**第 4 天**：
- 召回对比
- 制作对比表

| 维度 | Kimi K3 | GPT-4 | Claude Opus |
|------|---------|-------|-------------|
| 成本 | 20元/次 | ... | ... |
| 性能 | ... | ... | ... |
| 场景 | ... | ... | ... |

**结论**：基于数据选出最合适方案

**真实案例**：

问题："我要设计一个智能文档分析系统，Kimi K3 适合吗？"

基于 OKS 召回的答案：
- ✅ 效果强：2026 WAIC 发布，最强国产大模型
- ❌ 成本极高：20元/次 × 100文档/天 = 2,000元/天 = **60,000元/月**
- **结论**：不推荐作为主力模型

## 工作流 3：项目维护

**场景**：维护开源项目或团队代码库，需要记录决策和踩坑。

### 流程

```
1. 每次重要决策 → 写决策文档 → 收录 OKS
   ↓
2. 踩坑后 → 补充 anti-pattern 到 Wiki
   ↓
3. 新人 onboarding → 召回项目知识
   ↓
4. 定期审查 → 更新过时知识
```

### 技巧

**用 `supersedes` 更新过时决策**

```yaml
---
title: 为什么选择 PostgreSQL 15
supersedes: why-postgresql-14
---
```

**用 `challenges` 记录争议点**

```yaml
---
title: PostgreSQL 在 Windows 上的性能问题
challenges: why-postgresql
---
```

**建立项目 profile**

在 `profiles/projects/` 下创建项目档案

### 示例

**决策记录**：
- 问题：为什么选择 PostgreSQL 而不是 MySQL
- 收录：技术选型文档 → Wiki

**踩坑记录**：
- 问题：PostgreSQL 在 Windows 上的性能问题
- 收录：踩坑经验 + 解决方案 → Wiki

**新人 onboarding**：
- 新人问："为什么用 PostgreSQL？"
- 召回：决策文档 + 踩坑经验
- 节省沟通时间

**知识更新**：
- 半年后：PostgreSQL 15 解决了性能问题
- 更新：创建新 Wiki，supersedes 旧版本

## 工作流 4：团队协作

**场景**：团队共享知识库，避免重复踩坑。

> **注意**：OKS 设计为单人使用，团队共享需要约定规范。

### 流程

```
1. 每个人维护自己的 OKS 实例
   ↓
2. 定期导出高价值 Wiki → 团队共享目录
   ↓
3. 其他人导入到自己的 OKS
   ↓
4. 团队会议时召回相关知识
```

### 技巧

**用 git 管理知识库**
- OKS 是文件系统，天然支持 git
- 用 PR 流程审核知识

**建立团队 profile**
- 在 `profiles/teams/` 下创建团队档案

**定期同步**
- 如每周 sync 一次
- 避免冲突

### 注意事项

**OKS 的限制**：
- ❌ 没有权限管理
- ❌ 没有冲突解决机制
- ❌ 没有协作审核流程

**可行的团队模式**：

**模式 1：各自维护 + 定期同步**
- 每人维护自己的 OKS 实例
- 定期导出高价值 Wiki → 共享目录
- 其他人选择性导入

**模式 2：用 git 管理共享知识库**
- 用 PR 流程审核知识
- 用 git 解决冲突

**模式 3：建立团队规范**
- 统一的 Wiki 模板
- 明确的审核标准
- 定期的知识同步会议

**推荐实践**：
- 个人知识：自己的 OKS
- 团队知识：共享 git repo（手动维护）
- 不要把 OKS 当成团队 Wiki（用 Notion/Confluence）

## 时间估算

| 工作流 | 收集时间 | 审核时间 | 召回时间 | 总时间 |
|--------|---------|---------|---------|--------|
| 日常学习 | 5-10 分钟/周 | 20-30 分钟/周 | 自动 | ~40 分钟/周 |
| 技术选型 | 1-2 小时 | 30-60 分钟 | 10-20 分钟 | ~3 小时 |
| 项目维护 | 按需 | 按需 | 自动 | 碎片化 |
| 团队协作 | 按需 | 按需 | 自动 | 碎片化 |

## 效果对比

### 有 OKS vs 没有 OKS

| 维度 | 没有 OKS | 有 OKS |
|------|---------|--------|
| **知识来源** | AI 训练数据（可能过时） | 你看过的最新资料 |
| **数据准确性** | 模糊（"可能比较贵"） | 具体（20元/次、300+元） |
| **可追溯性** | 无法验证 | 关联到原始资料 + Provider 链 |
| **时效性** | 依赖模型更新 | 看完资料立即可用 |
| **个性化** | 通用回答 | 基于你关注的特性 |
| **决策质量** | 缺乏依据 | 有理有据，引用具体数据 |

**核心收获**：从"看过这个视频"到"能用它做技术选型"，只需 7 分钟。
