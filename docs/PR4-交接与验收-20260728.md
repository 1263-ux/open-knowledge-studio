## 1. 项目做什么

Open Knowledge Studio（OKS）是文件优先的知识工程 CLI。它把来源材料保留为可追溯的 Raw Bundle，经 Agent 生成 Candidate 后，再由人审核晋升为 Wiki 知识，最终供 `search` / `recall` 召回。

```text
来源采集 -> Raw Bundle（内容 + evidence + provenance）
         -> Candidate（Agent 提议）
         -> 人工审核
         -> Wiki
         -> 搜索 / 召回
```

提取器与飞书控制面是可选组件：不安装飞书、不配置飞书，核心 CLI 和本地知识链路仍可运行。

## 3. 当前能力边界

- Raw 是来源和证据，不等于已确认知识；系统不会自动把 Raw 晋升到 Wiki，人工审核仍是必要关卡。
- 飞书是可选控制面，不是核心链路的前置条件；未配置飞书时不能声称具备飞书提交、监听或审核能力。
- 本轮以本地模拟、单元测试和 CLI smoke 为主；真实飞书 Base 的完整 E2E、审核监听和多机部署未在本轮执行。
- 本地 lease lock 只保证单台主机内的串行认领；多机运行需要数据库租约、Redis 或其他外部协调，当前不支持分布式互斥。
- 视频、PDF、OCR 和 Web 提取依赖外部工具、模型、网络与平台策略；“可安装”不等于任意 URL、受限内容或反爬环境必然可提取。
- 搜索与召回面向已晋升 Wiki；Raw 到 Candidate 的理解质量依赖 Agent 和人工审核，并不等价于事实校验。

## 4. 已知问题与合并门槛

当前复核发现一个必须在请求上游重新审核前处理的 P0：

```text
feishu-base://{base_token}/{table_id}/{record_id}
```

`scripts/feishu_worker/capture.py` 当前将 Base token 放入 `source_uri`。该 URI 会被写进运行产物和 Raw Bundle；即使 `.oks/` 被忽略，token 仍不应进入任何持久化数据面。修复应改用不含认证信息的稳定标识，例如 `feishu-base://{table_id}/{record_id}`，并新增回归测试，断言 bundle、candidate 和运行记录均不包含 token。

因此，PR 目前应视为“核心上游阻断项已修复、但存在一个新发现的凭据持久化 P0 待修复”，而不是可直接请求 approve 的最终状态。

## 5. 下一步设想（按优先级）

1. 修复 `source_uri` 的 token 持久化，并以当前 PR 头提交重新执行安全审查。
2. 在干净服务器按 `/accept` 的隔离流程逐项验证 document、pdf、formula、watch、feishu；报告要明确区分产品失败、环境受限与未执行。
3. 用专用且可删除的飞书 Base 做真实 E2E：提交、Worker、审核事件、晋升与召回；凭据只在运行时环境变量中提供。
4. 若需要多机 Worker，设计并实现分布式租约；在完成前继续明确标注仅支持单机串行。
5. 继续降低 facade 的依赖注入复杂度，并为跨模块契约增加更少依赖 monkeypatch 的集成测试。
