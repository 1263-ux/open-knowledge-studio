# 托管你的简历

{: .important }
> **状态：已完成脱敏岗位对照。** 本案例使用一份真实简历和公开岗位要求，形成面向 Agent 应用开发的候选表达与能力缺口清单。它不证明已投递、获得面试或拿到 offer。

## 结果摘要

| 项目 | 本案例实际发生的事 |
| --- | --- |
| 场景 | 一份通用后端简历需要转成面向 Agent 应用开发岗位的候选材料。 |
| 输入 | 脱敏后的真实履历，以及公开职位中的岗位要求。 |
| Agent 完成 | 归纳岗位要求，逐项映射已有证据，并标出不能补写的能力缺口。 |
| 人做的决定 | 核对每条项目描述、技术深度与数字是否真实；决定哪些内容可以进入候选简历。 |
| 最终交付物 | 一份岗位匹配表和候选简历写作方向；原简历与身份信息不公开。 |
| 仍未验证 | 候选简历的人工最终版、投递结果、面试表现，以及未列出的工程能力。 |

## 目标不是“把简历写得像高手”

目标岗位是**初级 / 校招 Agent 应用开发**，而不是资深 Agent 平台架构师。公开岗位通常要求：后端开发基础、LLM 应用模式、RAG 或知识库、工具调用与工程化交付；更成熟的岗位还会要求评测、可观测、失败处理和线上运行经验。

本案例只把已有经历组织成对岗位有用、且可以追溯的表达；没有做过的事不会因为关键词匹配而写进简历。

## 真实输入，先做脱敏

原始简历中的姓名、电话、邮箱、学校、公司、地点、时间与薪资都不进入公开页面或截图。公开案例只保留与判断有关的事实：技术栈、项目类型、候选岗位与证据边界。

本轮材料里可确认的基础包括：Java / Spring Boot 后端、MySQL 与 Redis、Docker、OpenAI API、LangChain4j、RAG、Embedding、向量检索，以及医疗问答和微服务项目实践。这些是材料中的自述，仍须由本人核对其实际实现范围。

## Agent 先给出匹配表，而不是直接重写

| 目标岗位关心什么 | 已有材料能支持什么 | 不能替人补写什么 |
| --- | --- | --- |
| LLM 应用与 RAG | 有 LangChain4j、OpenAI API、Embedding、向量检索与医疗问答项目的材料 | 生产环境效果、准确率、并发和成本 |
| 后端工程 | 有 Java、Spring Boot、MySQL、Redis、Swagger / OpenAPI 与 Docker 的材料 | 架构负责人或大规模线上运维经历 |
| Agent 工作流 | 有 Agent 工作流实践与持续关注该方向的材料 | MCP / Tool Calling 的实际交付、复杂规划能力 |
| 交付质量 | 有容器化和项目实现材料 | 评测集、回归测试、Trace、监控与失败恢复 |

这个表的作用是让人先看到“证据在哪儿、缺口在哪儿”。它不是自动打分，更不是把关键词堆进技能栏。

## 人工审核后，候选简历应该强调什么

审核者可以接受的写作方向是：

1. 用一个明确项目讲清楚 RAG 链路：资料如何进入知识库、如何检索、回答如何受来源约束。
2. 把 Java 后端和 Docker 写成让 Agent 应用能运行的工程基础，而不是与目标岗位无关的技术罗列。
3. 对尚未具备的 MCP、评测、可观测能力如实写为学习或待补项目，不伪装成生产经验。
4. 为每条简历主张保留可复查的代码、设计说明、截图或人工确认记录。

## 这张案例还不能证明什么

- 不证明候选人具备资深平台设计、线上高并发或复杂多 Agent 编排经验。
- 不证明任何项目的规模、效果、用户数量或商业成果。
- 不证明简历已投递、通过筛选、进入面试或获得 offer。
- 不把接触过的技术自动等同于独立交付过的能力。

## 用自己的岗位重新运行

1. 提供一份履历和一个具体 JD；先移除不应交给 Agent 或公开页面的个人信息。
2. 要求 Agent 逐条列出：岗位要求、简历证据、待核实项和能力缺口。
3. 人工确认项目事实，再让 Agent 起草对应版本；不要先让它“优化”。
4. 渲染后检查版式与事实，投递后再把反馈记录为新的材料，而不是倒填为成功经验。
