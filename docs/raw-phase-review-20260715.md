# Raw 多模态第一阶段复盘

> 日期：2026-07-15  
> 参与：Codex、Claude（DeepSeek 后端）  
> 目标：判断当前实现是否符合“多模态信息处理，抽取成可追溯 Raw Markdown”的项目预期。

## 1. 共同结论

当前实现已经达到：

> **本地文件 Raw 提取第一阶段完成。**

当前实现尚未达到：

> 生产级全来源多模态入口、真实平台字幕稳定提取、所有内容高保真自动解析。

核心目标的第一版骨架成立：

```text
本地视频/音频/图片/PDF/Office/HTML
  → 成熟提取器
  → Raw Markdown + Evidence + Assets + Metadata
  → 机械校验
  → OKS召回
```

Raw 边界保持正确：没有摘要、自动纠错、概念抽取、内容评级、Wiki 决策或自动晋升。

## 3. 真实暴露的问题

### 3.1 上游提取误差

#### 公式

MinerU 能保留大量公式结构，但已经出现会改变数学语义的错误：

- 将区间或关系符号识别为 `\rceil`、`\ddagger`；
- 混入错误希腊字母、垂直符号和重复 `\perp`；
- 上下标、根式、对数底数和表格结构变形；
- 正文与公式边界混合。

这说明“公式可检索”已经存在，但“公式可直接信任”没有实现。

#### ASR

真实音频中出现：

- “键盘录入”→“键盘录录”；
- “较大值”等词被识别为语义相近或无意义文本；
- 技术名词、口音、连读和标点不稳定。

时间戳仍然保留，因此可以回到原时段核查。

#### OCR

整屏截图中会混入：

- 菜单栏、状态栏、会议控件和图标文字；
- `Fo`、`008s` 等无意义片段；
- 单字符和低置信度噪声；
- 多栏和复杂界面阅读顺序不稳定。

bbox 和置信度已经保留，但当前没有用户选区或正文区域约束。

### 3.2 视频视觉能力不足

当前所有真实视频 metadata 中的视觉路线均为 `uniform`。这意味着：

- 场景检测接口存在；
- 没有真实样本证明它能稳定找到场景切换；
- 当前关键帧实质上是均匀回退后的候选帧；
- 对代码演示、PPT逐步变化和板书过程可能遗漏关键状态。

该限制已经写入 warning，因此没有静默伪装为场景检测成功，但不能对外宣称“智能关键帧选择已完成”。

### 3.3 平台入口没有闭环

- 三个B站样本均无公开字幕；
- yt-dlp 请求遇到 HTTP 412；
- 平台字幕、登录态媒体获取和URL→ASR完整回退未在真实平台闭环；
- 本地下载后ASR成功不能替代“平台URL能力成功”。

### 3.4 可追溯与消费端诚实性

已经发现：

- `doctor` 能读出工具版本，但当前 Raw metadata 仍可能写 `extractor_version: unknown`；
- PDF、视频和音频通常只记录原文件绝对路径与SHA-256，不复制大文件；源文件移动后回查能力下降；
- PDF和MarkItDown的 `content.md` 没有像视频/图片一样在正文顶部醒目标明“机器提取、未经校对”；
- 普通 Recall 主要展示 `content.md` 片段，不一定同时展示 `quality-report.json` warning，错误公式可能在无提示情况下进入召回片段；
- Windows旧代码页输出数学Unicode字符时，`oks recall` 的Rich展示可能报GBK编码错误，数据检索本身仍成功。

### 3.5 已修复的打包错误

Claude抽查发现视频/音频 `raw.md` 曾将逐字稿段数写成字面量：

```text
{len(transcript_segments)}段
```

该问题属于我们自己的打包错误，不是模型误差。本轮已改为真实数字并增加回归断言。

## 4. 什么错误仍算合格Raw

Codex和Claude一致认为，Raw不以“自动识别全对”为验收标准。以下条件同时满足时，上游识别错误仍可以作为合格Raw保留：

1. 内容明确标注机器提取、未经校对；
2. 每条内容能回到页码、时间戳、bbox或原始资产；
3. 已知误差类型在 warning 中显式出现；
4. 被跳过或失败的模态没有静默消失；
5. 提取器原始结果和可读整理层没有被伪装成人工确认知识。

以下情况不应视为合格：

- 正文为空却标记成功；
- 某个模态未执行但没有记录；
- 图片、页码、时间戳或资产断链；
- 召回片段把机器误识别伪装成已确认事实；
- 产物数量与提取器交付数量不一致；
- 平台失败被本地文件回退结果冒充成功。

## 5. 双方分歧

### 原文件是否必须复制进Bundle

Claude观点：

- Raw不是原文件备份系统；
- `local_path + SHA-256` 已能证明来源；
- 不应把数百MB视频和大量临时中间结果全部复制进长期Raw；
- 该问题不阻塞第一阶段收尾。

Codex观点：

- 不应默认复制所有大文件，认同避免Raw无限膨胀；
- 但绝对路径会随文件移动失效，仅有Hash不能恢复证据；
- 应明确 `copied / referenced / unavailable` 源资产策略；
- 小型PDF、网页快照和图片适合复制，超大媒体适合进入内容寻址源仓或保持受管引用；
- 这是长期可追溯性缺口，但不必阻塞“本地原型完成”的命名。

双方一致：提取器版本为 `unknown` 应补齐，但不是第一阶段核心链路的阻塞项。

## 6. 是否可以收尾

可以带边界收尾，正式表述应为：

> 本地文件多模态 Raw 提取第一阶段已完成。视频、音频、图片、PDF、PPT、Word和静态HTML可以进入统一Raw v0.1并被校验和召回。平台字幕、登录态页面获取、真实场景切换关键帧和高保真公式识别尚未完成。

不应表述为：

- 已支持现实世界所有信息；
- B站/抖音链接可以稳定直接解析；
- 数学公式已经可靠；
- 智能关键帧已经完成；
- Raw 可以无人确认直接成为Wiki知识。

## 7. 下一步只做三件事

1. **补齐诚实消费链**：注入真实提取器版本，让可召回 `content.md` 显示机器提取提示，并明确源资产 `copied/referenced` 策略。
2. **补三类缺口样本**：真实场景切换视频、确有字幕的登录态B站视频、公式密集页；只验证能力是否存在，不打内容质量等级。
3. **实现最小登录态捕获入口**：浏览器扩展通过用户点击获取当前页面、字幕/正文、选区、截图和保存原因，形成Capture Envelope并交给现有Raw Pipeline；飞书随后作为移动端收件箱接入。

一句话评价：

> 我们已经证明“现实本地素材能进入AI可用的Raw状态”，还没有证明“所有平台内容都能高保真、免维护地进入长期知识系统”。
