# OKS 最佳实践

> 三个阶段，每个阶段一个核心原则。

---

## 核心流程

```
Raw（收集） → Draft（审核） → Wiki（使用） → Recall（召回）
```

**关键理念**：OKS 不是笔记软件。它把你**已经看过的资料**，变成**未来能找到的知识**。

---

## 阶段 1：收集 Raw

### 原则：只收你真正看过的

**✅ 应该收集**：
- 看完的视频、文章、书籍
- 包含具体数据的资料（成本、性能、结论）
- 未来需要追溯来源的内容

**❌ 不要收集**：
- 没看过的"收藏链接"
- 纯娱乐内容
- 敏感信息

**💡 技巧**：A/B/C 分级
- A 级：必审必晋升（核心资料）
- B 级：选择性晋升（一般资料）
- C 级：只保留 Raw（参考资料）

---

## 阶段 2：审核 Draft

### 原则：三个检查点

1. **准确性**：事实是否正确？有没有 AI 幻觉？
2. **可复用**：三个月后还能用吗？
3. **可追溯**：能找回原始资料吗？

**❌ 常见错误**：
- 不审核直接晋升
- Draft 堆积超过 20 个
- 晋升后不测试召回

**💡 技巧**：问自己"三个月后我会用到吗？"

---

## 阶段 3：召回 Recall

### 原则：用自然语言，不是关键词

**✅ 好的提问**：
```bash
oks recall "Kimi K3 适合用来做文档分析吗？"
```

**❌ 不好的提问**：
```bash
oks recall "Kimi K3 文档 成本"
```

**为什么召回不准？**
1. Draft 还没晋升 → `oks wiki list` 检查
2. 用词不匹配 → 换个措辞试试
3. 类型权重低 → 改 frontmatter 的 `type`

**💡 调优**：
- 用 `--explain` 查看评分详情
- 设置 goal 提升相关领域权重

## 常见工作流

### 日常学习
```
看文章/视频 → 周末审核 Drafts → 写方案时自动召回
```

### 技术选型
```
收集 3 个方案资料 → 沉淀核心特性 → 召回对比 → 决策
```

### 项目维护
```
重要决策 → 收录 OKS → 踩坑补充 → 新人召回
```

## 快速问答

**Q: 为什么召回找不到？**  
A: 1. 检查是否晋升 `oks wiki list` 2. 换个措辞 3. 用 `--explain` 看详情

**Q: Draft 太多怎么办？**  
A: A/B/C 分级，批量 reject 不需要的，每周固定时间审核

**Q: 成本和性能？**  
A: 50个 Wiki < 100ms，视频转写免费（本地 faster-whisper）

**Q: 适合团队用吗？**  
A: OKS 是个人工具。团队可以各自维护 + 定期同步高价值 Wiki
