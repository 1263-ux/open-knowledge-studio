触发 Mail Core 或协议变更。

## Product signal

- BETA-12、BETA-13、BETA-14、BETA-15 的真实 Agent 任务均保持
  `context_reask_count=0`、`duplicate_work_count=0`、`unresolved_thread_count=0`。
- BETA-14 证明两个 Claude Session 可以在同一 durable Thread 上接力：A 产出
  `decision_pending`，B 读取 A 的结果并产出唯一最终决策。
- BETA-15 证明 `presented → acknowledged` receipt 与 Thread 结果语义可以被
  Agent 正确验证，且 `acknowledged` 不会被误当成工作完成。
- 因此当前 Mail Core 的核心产品假设仍成立：协作结果可以持久化在 Thread，
  接手 Agent 不需要重新询问上下文。

## Repeated root requiring RETHINK

BETA-14 与 BETA-15 的 Claude Session 都重复出现同一类执行面摩擦：Agent 先
使用不存在的 `--session`，再根据错误改成 `--session-id`；并且曾把 message ID
传给要求 Thread ID 的 `oks mail reply`。这些错误均自恢复，没有造成 Core 数据
损坏，但重复出现说明当前 CLI 示例/Agent 操作提示不够抗误用。

这不是 `delivery_failure`、`thread_confusion` 或 receipt 持久化失败，不应通过
新增生命周期状态、自动重试、Coordinator 或 wake 来掩盖。应在下一轮 Owner
决策中单独判断是否做向后兼容的 CLI ergonomics/runbook 改进，例如更明确的
`ack`/`reply` 帮助和交接模板；本聚合不直接修改 CLI 契约。

## Decision

1. 保持 Mail Core、Thread、receipt、ack 语义冻结。
2. 保持 DSH 为 observation-first 控制面，不增加聊天输入框或自动 wake。
3. BETA-16 暂停，避免在同一执行根因已重复后继续堆样本。
4. Owner 审核后，若只改执行手册/帮助文本，再用一项回归任务验证；若要改
   CLI 行为，先单独立项并保留兼容性测试。
